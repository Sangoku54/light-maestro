# 2026-08-23 — Bug « ça bug de partout » sur l'exe portable

## Cause racine (définitive, enfin trouvée)

Le `.exe` embarquait bien tout le code + les 2221 fixtures **standard**, mais
PAS les **fixtures personnalisées** de l'utilisateur. Elles vivent dans
`%APPDATA%\light-maestro\fixtures\` (`custom-tonio-6-arm.json`,
`custom-stage-right-stage-wash-7x10w-led-moving-head.json`), référencées par
`fixtureDefId` dans le `.lmproj`, mais leurs définitions n'étaient ni embarquées
dans l'exe, ni dans le fichier projet.

Sur le PC live (userData vierge) : `getDefinition('custom-tonio-6-arm')` →
`undefined` → tout ce qui référence ces fixtures casse (fixtures patchées,
scènes, chasers, **presets des widgets** → scènes → fixtures). C'est le « ça bug
de partout ».

## Preuve du diagnostic

- Lancé `release\win-unpacked\Light Maestro.exe` (même code que l'exe portable) :
  `fixture-library.log` → `packaged=true`, fixtures chargées (2220/2221), AUCUNE
  erreur de module natif (`better_sqlite3.node` dev == packagé, byte-identique,
  c'est du N-API donc ABI-stable → pas le problème).
- Les erreurs DMX `COM6 not found` = juste le dongle USB débranché, pas un bug.

## Fix appliqué (3 volets)

1. **Portabilité des fixtures custom** — nouveau `src/utils/custom-fixtures.ts` :
   `collectCustomFixtureDefs()` (embarque les defs custom dans le .lmproj) +
   `importCustomFixtureDefs()` (ré-importe via `fixtures:addCustom` au chargement).
   Branché dans : `App.tsx` (saveProject + __lm_open), `ShowManager.tsx`
   (save .lmshow + load), `PerformanceView.tsx` (VC loadShow). Le projet devient
   auto-suffisant, sans dépendre de userData.
2. **Embarquer les 2 fixtures custom actuelles** — copiées dans
   `resources/fixtures/custom/` → packagées dans l'exe. Le projet EXISTANT
   (sauvé avant le fix) fonctionne donc immédiatement sur le PC live.
3. **`library.ts add()` rendu idempotent** — `Map.set` toujours (mise à jour OK),
   mais `searchIndex.push` seulement si nouveau → évite les doublons de recherche
   quand une fixture custom embarquée + une userData coexistent.

## Effet de bord constaté (normal)

Compteur fixtures 2221 → 2220 au lieu de 2223 : 2 custom embarquées (+2), mais
1 fixture OFL « Stage Wash 7x10W » masquée car même `manufacturer+model` que la
custom (−1), et les copies userData écrasent les embarquées au lieu de s'ajouter
(−2). Les 2 custom sont bien présentes dans le Map (vérifié par le calcul exact).

## Validation

- `npx tsc --noEmit` (renderer) + `npx tsc -p tsconfig.electron.json --noEmit` → 0 erreur.
- `npx vitest run` → 208/208 pass.
- `npm run build` → exit 0 ; `npx electron-builder --publish never --win portable`
  → exit 0. Exe : `release\Light Maestro 1.0.14.exe` (78.9 MB, 23/08 10:05).
- Vérifié : `release\win-unpacked\resources\app\resources\fixtures\custom\`
  contient les 2 JSON ; le JS renderer contient `customFixtures` ; le JS electron
  contient le `add()` idempotent (`const isNew = !this.fixtures.has(def.id)`).

## Reste à faire (côté utilisateur)

- Tester l'exe sur le PC live avec le projet existant (les 2 custom sont embarquées).
- Recommander de **re-sauvegarder** le projet avec la nouvelle version (Ctrl+S)
  pour embarquer `customFixtures` dans le .lmproj (future-proof : toute nouvelle
  fixture custom créée après ce build devra passer par l'embed/import, pas par le
  bundling statique).

## Leçon

Quand l'utilisateur dit « l'exe appelle des fichiers locaux », ne pas se limiter
à auditer les chemins hardcodés dans le code : auditer AUSSI les **données
utilisateur** (userData/fixtures, shows, presets) référencées par les fichiers
projet. C'était ça le vrai problème.
